# Лабораторная 3 по дисциплине "Технологии программирования"

**Тема:** изучение модульного тестирования приложений. **Вариант:** 11.

## Постановка задачи

Написать модульные тесты к проекту, разработанному в лабораторной работе № 2,
— интернет-магазину товаров для сада на Django
([PTLab2](https://github.com/USERNAME/PTLab2)).

Логика проекта (вариант 11): у каждого товара есть начальное и текущее количество
на складе; после покупки количество уменьшается; если оно уменьшилось **более чем
в два раза**, цена товара однократно возрастает на 20 %; закончившийся товар купить нельзя.

## Что сделано

- набор тестов расширен с 26 до **89 тестов** (116 проверяемых случаев с учётом
  `subTest`), тесты разделены по слоям приложения;
- достигнуто **100 % покрытие** кода приложения (`shop/`, без миграций и тестов);
- в GitHub Actions покрытие проверяется автоматически: `coverage report --fail-under=100`
  завершает сборку с ошибкой, если покрытие станет меньше 100 %;

## Используемые технологии

- Python 3.12, Django 5.2, PostgreSQL 16;
- `django.test`: `TestCase`, `SimpleTestCase`, тестовый клиент `Client`,
  `assertContains`, `assertTemplateUsed`, `assertFormError`, `CaptureQueriesContext`;
- `unittest`: `subTest`, `unittest.mock.patch.dict`;
- `coverage` — измерение покрытия; GitHub Actions — CI.

## Запуск тестов

```powershell
$env:DATABASE_PASSWORD = "ur_db_password"
coverage run manage.py test shop
coverage report
coverage html        # отчёт в htmlcov/index.html
```

```text

```

## Выводы

1. Модульные тесты разделены по слоям MVC (модели, формы, представления, маршруты,
   админка, команды, настройки), поэтому при ошибке сразу видно, какой слой сломан.
2. Особое внимание уделено граничным значениям бизнес-правила варианта: «ровно в два
   раза» (цена не меняется) и «более чем в два раза» (цена +20 %), нечётное начальное
   количество, последний экземпляр, повторное повышение.
3. Тесты проверяют не только «счастливый путь», но и ошибки: покупка сверх остатка,
   закончившийся товар, неверные данные формы, несуществующий товар, запрос без CSRF-токена.
4. Достигнуто 100 % покрытие кода, а порог покрытия закреплён в CI, поэтому новый
   непротестированный код не пройдёт проверку.
5. Покрытие 100 % не гарантирует отсутствия ошибок: оно показывает, что каждая строка
   выполнялась, но не что проверены все комбинации данных. Поэтому дополнительно
   применены табличные тесты (`subTest`) для граничных случаев.
